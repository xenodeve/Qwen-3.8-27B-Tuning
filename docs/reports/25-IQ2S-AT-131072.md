# 25 — UD-IQ2_S at 131,072: the reserve is the only lever

**Measured 2026-08-21.** Raw: `qwen38-tuning/results/iq2s-131072-residency.jsonl`
(11 rows). Driver: the tested primitives in `bench/depth_sweep.py`; this report
only chose the arms.

## The question

Profile B ships `UD-IQ2_S` at 98,304 because 131,072 had been seen to load `60+5`
— five of 65 layers on the CPU. Two levers were never separated: `--fit-target`,
which sets the VRAM headroom `--fit` must leave, and `-b`/`-ub`, which size the
compute buffers. Either could plausibly buy the five layers back.

## Method

Two phases, each two rounds with the arm order reversed, because free VRAM at
boot moves 9,326–10,732 MiB and every cross-boot comparison inherits that. One
control at 98,304. `-ctk q4_0 -ctv q4_0`, `--spec-type ngram-mod`, `--fixed-text`,
and the low-repetition filler — the same decoder profile B actually ships, not
`draft-mtp`.

## Phase 1 — reserve and batch varied together

| arm | round | split | prefill tok/s | decode tok/s | KV MiB | free MiB |
|---|---|---|---|---|---|---|
| control @98,304 | 0 | `65+0` | 918.9 | **26.61** | 1,728 | 400 |
| `--fit-target 768` | 1 | `60+5` | 684.0 | 8.16 | 2,160 | 416 |
| `--fit-target 768` | 2 | `60+5` | 731.5 | 10.79 | 2,160 | 882 |
| `--fit-target 192` | 1 | **`65+0`** | 817.1 | **23.21** | 2,304 | 233 |
| `--fit-target 192` | 2 | **`65+0`** | 836.1 | **23.92** | 2,304 | 424 |
| `--fit-target 192 -b 1024 -ub 128` | 1 | `65+0` | 721.8 | 22.18 | 2,304 | 285 |
| `--fit-target 192 -b 1024 -ub 128` | 2 | `65+0` | 188.1 | 14.41 | 2,304 | 291 |

## What the rows say

**1. The batch size buys nothing.** All four phase-2 rows load `60+5`, identical
to the plain `--fit-target 768` rows, and they agree with each other to within
0.7 % on decode. Shrinking `-ub` from 256 to 128 does shrink the compute buffer,
but `--fit` then reserves the same 768 MiB anyway and the layers stay on the CPU.
**`--fit-target` is the only lever that moves the split.** This arm was added on
the recommendation of two independent reviewers who both named it as the missing
cell of the 2×2; the answer is a clean no.

**2. `--fit-target 192` makes 131,072 fully resident, twice.** `65+0`, decode
23.21 and 23.92 tok/s across reversed rounds — a 3 % spread. Against the 98,304
control's 26.61, the extra 32,768 tokens of window cost about **11 % of decode,
which is inside the 13.6 % drift floor.** On these two rounds the depth is close
to free.

**3. Leaving the reserve at its default costs 2.5–3× the decode.** 8.16 and 10.79
tok/s at `60+5` against 23.2–23.9 at `65+0`. Five CPU layers out of 65.

**4. Free VRAM at settle does not order the outcomes.** The fastest prefill in
the whole set, 836.1, sits at 424 MiB; the second fastest, 817.1, sits at **233
MiB** — the lowest reading recorded. The slowest, 188.1, sits at 291 MiB, with
*more* headroom than either. This contradicts the threshold published as
`CORRECTIONS.md` §13 and is now recorded as **§14**.

## What this changes

`UD-IQ2_S` can serve a 131,072 window on this machine. The cost is not the
context, it is the artifact: **23.2–23.9 tok/s against profile A's 45** at the
same depth. That is the real trade — roughly half the decode speed for the
IQ2_XXS → IQ2_S step in bits per weight — and it is now measured rather than
inferred from a vendor curve taken at 4,096 context.

**Not yet established.** Whether `--fit-target 192` is reproducible enough to
ship as a default. Plain `fit-192` is 2 for 2, but its small-batch sibling
collapsed to 188.1 tok/s in one round of two, and §14 says the free-VRAM reading
does not tell you in advance which you will get. Two rounds is a pilot.

**Not tested.** Moving the display to the Intel UHD 770. Every reviewer named it
as the largest available lever and no row here touches it; it remains untested
and so is not a finding.

## End to end at 131,072

The server was then started at `-c 131072 --fit-target 192` and driven by the
lean OpenCode profile on a real task — write `slugify.py`, write three asserts,
run them. **It passed:** the model wrote both files, executed
`python test_slugify.py`, and reported all three asserts green. `claude-xeno`
(Claude Code against the same server) answers and executes tool calls at this
depth too.

Two harness defects were found in the process and only one is fixed.

**Fixed: normal OpenCode.** With the user's full global config the server returns
`Failed to initialize samplers: failed to parse grammar` on every request. The
`vercel` MCP server's `buy_domain` tool carries a regex `pattern` that
llama.cpp's JSON-schema-to-GBNF converter cannot express; it warns
`Unsupported pattern syntax` and then emits GBNF containing `\-`, which is not a
valid GBNF escape. Disabling that one MCP server clears it. **An earlier run in
this session appeared to prove normal OpenCode healthy — it did not. It only
showed that the failure is intermittent, because it depends on which MCP servers
happened to connect.**

**Unresolved: `-Work` does not decide where OpenCode writes.** Five runs are
tabulated in the header of `qwen38-tuning/scripts/oc.ps1`. On this machine the
agent's own `pwd` returns `C:/AI` almost regardless of the working directory it
was launched in, and one run wrote its output files into the repository root and
reported success. Four explanations were tested and refuted: a stale OpenCode
server, `OPENCODE_CONFIG_DIR` inside the repository, a nested git root, and a
git root outside the repository. Until it is understood, put the absolute
destination path in the prompt and check where the files went.
