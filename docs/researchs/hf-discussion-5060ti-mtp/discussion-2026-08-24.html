I’ve been testing Qwen3.8-27B-GGUF (UD-IQ3_XXS) locally using llama.cpp (llama-server) on a single mid-range consumer GPU setup (RTX 5060 Ti 16GB + 32GB RAM), and the performance-to-VRAM ratio achieved with Multi-Token Prediction (MTP) is worth highlighting. Amazing job from Qwen team.

Here is a quick breakdown of the setup and execution parameters that brought inference speed from ~35 t/s up to a steady 50–55 t/s with a 94k context window.

Some notes:
Without MTP, average of 35 t/s
Without "reasoning_effort": "medium" , the model overthink too much ( the default is xhigh )
Setting parallel to 1, make possible up the context to 92K

  • Ensure only one health potion exists on screen at any time to prevent excessive power-ups

I found the issue. My llama.cpp install from Winget was using the Vulkan backend instead of CUDA.

After switching to the official CUDA build of llama.cpp, performance improved a lot.

I also noticed that CLI agents add a large system/tool prompt, so even a fresh session can already start with ~20k context. That explains why the coding agent is slower than a raw API request.

With CUDA + MTP I now get around 50–57 tok/s on short context and roughly 40–50 tok/s in the coding agent.

This is the command I’m using (powershell):

llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-IQ3_XXS
--no-mmproj --device CUDA0
--spec-draft-device CUDA0 --gpu-layers-draft all
--spec-type draft-mtp --spec-draft-n-max 3
--n-gpu-layers all --threads 6
--fit off --load-mode none
--no-warmup --flash-attn on
--ctx-size 94208 --parallel 1
--cache-type-k q4_0 --cache-type-v q4_0
--batch-size 512 --ubatch-size 512
--jinja --temp 1
--top-p 0.95 --top-k 20
--min-p 0.0 --presence-penalty 0.0
--repeat-penalty 1.0 --reasoning auto
--reasoning-preserve --host 127.0.0.1
--port 1234

And I set:

LLAMA_ARG_CHAT_TEMPLATE_KWARGS={"preserve-thinking":true,"reasoning_effort":"medium"}

So if anyone has the same performance problem, first check whether llama.cpp is actually using CUDA and not Vulkan.

Thanks for this thread — it sent me down the MTP rabbit hole and the results on my 5060 Ti 16GB have been pretty wild.

I’m running Qwen3.8-27B UD-IQ4_XS rather than IQ3_XXS, on the official llama.cpp CUDA 13.3 build b10549, with the model fully on the 5060 Ti. My 3060 Ti handles Windows/monitors etc separately.

Current config:

Qwen3.8-27B UD-IQ4_XS
32K context
Q8_0 K + V cache
Flash Attention on
parallel=1
MTP draft layer fully on GPU
--spec-type draft-mtp
--spec-draft-n-max 3
RTX 5060 Ti 16GB

Without MTP I measured:

~2.5K context: 26.0 t/s
~14.2K: 24.9 t/s
~18.1K: 24.5 t/s
~25.4K: 23.7 t/s

With MTP n=3:

~2.5K: 54.1 t/s
~14.2K: 50.8 t/s
~18.1K: 51.3 t/s
~25.4K: 40.8 t/s

So it’s basically a 2x speedup through the context range I care about, while keeping the higher-quality IQ4_XS quant and Q8 KV.

Peak VRAM in the MTP n=3 tests was about 15.4GB, so it’s tight but fits cleanly. I also specifically checked for Windows shared-memory spill and didn’t find any.

One other interesting result: the GGUF definitely contains the Qwen MTP layer (qwen35.nextn_predict_layers = 1 / blk.64.nextn.*), so no separate draft model is needed.

I also tested reasoning effort. The model template supports xhigh / medium / low, with xhigh as default. Medium looks promising for coding quality, but it absolutely needs a bigger output budget — with a 3K-token ceiling it could spend the whole allowance reasoning and never emit the final answer. At 6K it completed and gave a stronger engineering analysis than thinking-off on my codebase.

So at the moment my likely production setup is:

IQ4_XS + Q8 KV + 32K + MTP n3 + medium reasoning for the higher-judgement roles.

Really appreciate the original numbers here — they gave me the clue to test MTP properly. I was expecting ~25–30 t/s from this card and am now seeing ~50 t/s at realistic coding-agent context sizes.

Has anyone else tried IQ4_XS + Q8 KV + MTP n3 on the 5060 Ti? I’d be interested to compare acceptance rates / VRAM / throughput.

Update after more coding-agent testing: I found another surprisingly large config effect. My original runtime used temp=0.2 / top_p=0.95 with thinking disabled. On the same deterministic coding canary, switching to Qwen's non-thinking sampling profile (temp=0.7, top_p=0.8, top_k=20, presence_penalty=1.5) produced the same correct 8/8 implementation, but tool-call repetition dropped from 30 to 0, requests from 53 to 4, and wall time from 374.9s to 42.2s. So on this model, overly conservative sampling appears capable of massively hurting agentic convergence even when final coding capability is unchanged.
