## What happened to the runs that are not in the table

- **B-noskill first attempt (09:34–10:49, timed out at 75 min, no page).** The runner's stop step deleted `exl3-stop.flag` three seconds after the kill, before the relaunch loop had read it, so the loop relaunched the *default* 4.0bpw model on top of the 3.5bpw boot every ~4 minutes (ten logs `exl3-serve-20260905-0932..1043`, each a full load ending in a bind error on :8000). With both cards within 0.6 GB of full the 3.5bpw server decoded at **9–10 tok/s** (prefill 110 tok/s) and after 10:21 printed `Synchronization timeout in kernel: pg_all_reduce_cpu_kernel` ×144 without a child dying — a *slow-but-alive* mode the watchdog does not catch. The rerun at 10:58, alone on the cards (7.7 / 10.9 GB), decoded at **62.7 tok/s** with zero timeouts. Same artifact, same recipe, same boot script: the only difference was VRAM headroom. This is the first same-day pair for issue #63's hypothesis A.
- **A-noskill's wall (6.5 min) carries ~4 min of waiting.** Its first request queued behind an orphaned request from a queue launch that was aborted at 09:24 (the server was still generating for the dead client); the server-side work of the cell is 15 s prefill + 144 s decode. Read 2.6 min, not 6.5, when comparing with B.
- **C-noskill first attempt (10:49–10:52).** llama-server booted while that stray EXL3 relaunch was loading; its first slot stalled at 710 of 788 prompt tokens and never produced a token (`C-noskill-r1-stuck/`). Restarted alone; the rerun is the C row above.
- **A-both-r1 (afternoon, 13:04–14:19, timed out at 75 min).** After writing the page and passing its own gate, the model started its Thai report and fell into a **repetition loop on the tone mark `่` (U+0E48)**: one API call produced a 127,682-character text message (`ทุ้่่่่ง 8 ข้อผ่านแล้้่่่่…`), 127,996 output tokens in 46 min at `reasoning effort = medium` — not thinking (that turn's thinking was ~80K chars, normal), not xhigh. The server's own line says what it was: draft acceptance **0.998** (95,958 of 96,111 draft tokens accepted), the drafter predicting a token that never changes. `CLAUDE_CODE_MAX_OUTPUT_TOKENS` = the whole window (the developer's 2026-09-04 setting) is what let it run: when it stopped, Claude Code compacted and re-prefilled 207,535 tokens (494 s). Second Thai-quality failure mode of the day, on the 4.0bpw H5 file this time (3.5bpw misspells; NVFP4-LOW showed neither). Once in ~40 Thai requests today; frequency unknown. A server-side loop guard is the fix that keeps the window cap (tuning-repo issue opened).
- **Every cell of the day carried the tuning repo's CLAUDE.md.** The work directories sat under `C:\AI\qwen38-tuning\results\…`, and Claude Code reads every ancestor `CLAUDE.md`; a `noskill` answer at 16:14 quoted the repo's *"no verdict before evidence"*. So `noskill` means *no skills*, not *no instructions* — the confound is the same in every arm, which leaves the arm comparison intact but makes the absolute `noskill` numbers those of a model already told to be careful and to answer in Thai. Cells run after 16:20 work in `D:\qbench-work` (no `CLAUDE.md` in any ancestor).
- Fixes shipped for both: the runner no longer deletes the stop flag; `serve-exl3.cmd` refuses to relaunch when :8000 already answers and counts a death within 420 s (a model load is 2–4 min) toward the give-up guard. `bench/tests/test_exl3_watchdog.py` pins both.
